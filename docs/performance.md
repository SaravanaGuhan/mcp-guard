# Performance

Comparison against the profile taken before the optimisation work. The README
carries current absolute numbers only; this file is where the before and after
belong, because the comparison is its subject.

Both profiles are committed and regenerated by `make profile`:

- `docs/profile-baseline.md`, taken at the start of the optimisation work
- `docs/profile-after.md`, taken at the end

Corpus: the 9 fixtures in `tests/fixtures/` plus 12 MCP server repositories
cloned from GitHub. Environment: Python 3.11.9, Node 24.13.0, Windows.

## Headline

| | before | after |
|---|--:|--:|
| Targets reaching an MCP handshake | 2 / 21 | 8 / 21 |
| Static parses per file | 3 | 1 |
| Test suite wall time | 51.8 s | 17.2 s |

A probe that never runs finds nothing, so launch success is the metric that
governs how much of the dynamic engine is reachable at all.

The baseline walked the tree four times and parsed every file three times, once
each for the AST rules, the MCP rules and the secret rules. python-sdk showed
899 unique files against 2,575 parse calls. Both are now once.

### Parallelism, tried and reverted

A `ProcessPoolExecutor` across the file inventory was slower than serial on
every repository tested, cold cache, milliseconds:

| repository | files | serial | pool |
|---|--:|--:|--:|
| typescript-sdk | 986 | 4,878 | 6,289 |
| python-sdk | 899 | 3,337 | 5,031 |
| mcp-server-cloudflare | 291 | 744 | 1,275 |
| github-mcp-server | 270 | 983 | 1,693 |

Windows has no fork, so each worker pays a fresh interpreter start and a
tree-sitter import, and every finding is pickled back. Per-file work is a few
milliseconds, far too little to amortise that. The code path remains behind
`parallel=True` for anyone re-measuring on a forking platform;
`PARALLEL_THRESHOLD` is `None`, so nothing enables it.

## Dynamic analysis

Milliseconds.

| target | before | after | change |
|---|--:|--:|--:|
| fixture/clean-server | 10,033 | 2,247 | -78% |
| fixture/vulnerable-server | 10,071 | 2,239 | -78% |
| real/mcp-server-airbnb | 45,952 | 12,228 | -73% |
| real/firecrawl-mcp-server | 27,555 | 10,830 | -61% |
| real/servers | 8,147 | 2,745 | -66% |
| real/Figma-Context-MCP | 24,549 | 17,919 | -27% |
| real/playwright-mcp | 3,312 | 3,323 | 0% |

The baseline was timeout accumulation rather than work. On clean-server,
`jsonrpc-conformance` spent 4,024 ms over five sends and
`malformed-frame-crash` 4,015 ms over five, while every probe that finds
something totalled 2.1 ms. Probe deadlines now derive from the measured
handshake round trip, capability-gated probes are pipelined with a window of
four, and `--probe-budget` bounds total probing.

`real/tavily-mcp` measured 8,200 before and 13,626 after. That is variance in
the Tavily API its tools call, not a regression: the code path is identical to
firecrawl's, which improved 61%. Probes against network-backed tools are
inherently noisy, and the budget bounds the worst case rather than the average.

## Dependencies

Figma-Context-MCP, 551 packages, 92 advisories, cold caches.

| | before | after |
|---|--:|--:|
| End to end | 66,065 ms | 17,814 ms |
| Second scan, warm caches | | 1,141 ms, 0 network requests |
| Console output | 209 lines | 61 lines |
| Findings from 92 advisories | 92 entries | 21 grouped |

Advisory records were fetched one at a time after the batch query; a
551-package repository issued about 90 sequential requests. They now run
through an eight-worker pool. The dependency stage also starts on a worker
thread before static runs, which hides the static stage behind the network,
worth 893 ms here.

`vuln-deps` went from 34 entries to 4, one per package, with every advisory id
preserved in evidence.
